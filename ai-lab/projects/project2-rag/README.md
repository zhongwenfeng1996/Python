## 实测指标（不是"看起来能答"）

**评估集**：**56 条**（52 可答 + 4 不可答），每条 `gold_doc` 与 `must_contain` 都经脚本机械校验。
**语料**：仓库自己的 24 篇 Markdown，**排除 project2 自己的文档**防评估泄漏。
**embedding**：本地字符 n-gram 哈希（无 API Key，确定性可复现）。

> ⚠️ **指标必须注明评估集版本。** 评估集在 2026-10 从 30 条扩到 56 条，
> 同时把「改写问句」占比从 11.5% 提高到 **44.2%** —— **指标全面下降，但那才是真实水平**。
> 详见 [ADR-008](docs/ADR.md#adr-008评估集必须包含足量改写问句否则指标会自欺)。
> 下面是**新评估集**的数字。

### 检索通道对比（切块策略 `heading`，k=5）

| 通道 | recall@5 | MRR | hit@1 | 耗时 | 要 API |
|---|---|---|---|---|---|
| dense（向量） | 0.4615 | 0.2833 | 0.1731 | 0.5s | 否 |
| **sparse（BM25）** | **0.9038** | **0.6478** | 0.5000 | 0.3s | 否 |
| hybrid（RRF 融合） | 0.7308 | 0.4821 | 0.3077 | 0.8s | 否 |
| rerank（词法重排） | 0.8462 | 0.6385 | 0.5000 | 1.1s | 否 |
| **llm（LLM 语义重排）** | **0.9808** 🏆 | **0.8638** 🏆 | **0.7885** 🏆 | 2873s | **是** |

**LLM 重排 vs 纯稀疏：**

| 指标 | sparse | llm | 提升 |
|---|---|---|---|
| recall@5 | 0.9038 | **0.9808** | **+0.077** |
| MRR | 0.6478 | **0.8638** | **+0.216（+33%）** |
| hit@1 | 0.5000 | **0.7885** | **+0.288（+58%）** |

> **这是全项目最有说服力的一张表**：它验证了前面所有推断 ——
> "词法方案弱在同义改写" → 补上语义信号后 **hit@1 从 0.50 提到 0.79**。
> 代价是 **11000 倍的时间**（0.3s → 2873s），所以怎么选见下面的成本曲线。

### LLM 重排的成本-效果曲线（候选池取多少）

| 候选上限 | recall池 | recall@5 | MRR | hit@1 | 打分次数 | vs全池 |
|---|---|---|---|---|---|---|
| 10 | 0.9423 | 0.9231 | 0.8221 | 0.7500 | 520 | 12% |
| **15** | 0.9423 | 0.9423 | **0.8606** | **0.8077** | 780 | **17%** |
| 30 | 0.9423 | 0.9231 | 0.8462 | 0.7885 | 1560 | 35% |
| 50 | 0.9808 | 0.9423 | 0.8510 | 0.7885 | 2600 | 58% |
| 95（全池） | 1.0000 | **0.9808** | 0.8638 | 0.7885 | 4475 | 100% |

**两个反直觉发现**：

1. **15 个候选就饱和了。** 15 → 95 是 **5.7 倍成本**，换来 MRR +0.003（≈0.15 条题）
2. **候选给太多反而伤 hit@1**：15 个时 0.8077，95 个时降到 0.7885 ——
   **噪音把正确答案挤下去了**

> **实践建议**：日常用 `--llm-max-candidates 15`，成本只有全池的 17%、
> hit@1 反而更高。答案质量绝对优先时才上全池
> （recall@5 从 0.9423 提到 0.9808，代价 5.7 倍钱）。

### 切块策略对比（新评估集，通道 `sparse`，k=5）

| 策略 | 块数 | recall@5 | MRR | hit@1 |
|---|---|---|---|---|
| `fixed`（固定字符硬切） | 352 | 0.8462 | 0.6240 | 0.4808 |
| `paragraph`（每段一块） | 1344 | 0.7885 | **0.6490** | **0.5577** |
| `heading`（按标题分节，默认） | 489 | **0.9038** | 0.6478 | 0.5000 |

**三者的权衡在新评估集上更清楚了**：

- `heading` 的 **recall 最高**（0.9038）—— 不丢答案
- `paragraph` 的 **MRR / hit@1 最高**（0.6490 / 0.5577）—— 小块更聚焦，命中时排得更前
- `fixed` 全面垫底 —— **不管结构硬切字符，是最差的选择**

选 `heading` 为默认的理由（在 ADR-001 里有完整论证）：
**在 RAG 里漏掉正确答案的代价更大**（模型没拿到资料就一定答错），
而排序差只是 prompt 里多几条噪音。且 `heading` 块数少 3 倍，索引与检索成本更低。

## 从数据里读出来的八件事（都是反直觉的）

### 1. 稠密检索"找得到但排不好"，而且原因清楚

把 k 拉大就能看出问题所在：

| k | dense recall | dense MRR |
|---|---|---|
| 1 | 0.3462 | 0.3462 |
| 5 | 0.6538 | 0.4545 |
| 20 | 0.8462 | 0.4694 |
| 100 | **1.0000** | 0.4726 |

**recall@100 已经是 100%（26 个目标全部能找到），但 MRR 几乎不涨（0.4545 → 0.4726）。**
结论：不是"检索不到"，是**排序差** —— 它把大量不相关块排在前面。

这**正是 ADR-002 预告的"语义泛化弱"**。当初写的是定性判断，现在有了定量证据：
本地字符 n-gram 只认字面重叠，而评估集里的问题大量是**改写问句**
（问"为什么日志要用 flush"，文档里写的是"块缓冲"），字面不重叠就排不到前面。

> **这说明一件事**：想在 RAG 上拿到好看的数字，**换 embedding 比调检索算法有效得多**。
> 这条结论只有先跑出基线才说得出来。

### 2. 混合检索**没有**更好 —— RRF 会被弱通道拖累

直觉是"混合一定比单一好"。实测：hybrid 0.7692 **低于** sparse 1.0000。

原因在 RRF 的公式：

```
RRF(d) = Σ 1/(k + rank_i(d))        k = 60
```

`rank_i(d)` 是**文档在该通道里的排名**，不是分数。所以：

- sparse 排第 1 的块 → `1/61 ≈ 0.0164`
- dense 排第 1 的块 → 也是 `1/61 ≈ 0.0164`
- **两路各取 30 个候选**，dense 的 30 个里即使大多不相关，也每个都拿到 `1/61 ~ 1/90` 的分

稀疏的排名是准的，但它的候选池被稠密塞进了 30 个"排名靠前但其实不相关"的块，
融合后把真正的好结果挤到后面。

**教训**：混合检索的前提是**两路都别太差**。一路明显弱时，融合只会拉低整体。
正确做法是先提升弱通道（换 embedding），再混合；或者给弱通道降权 —— 但降权需要数据支撑，
不能凭感觉。

### 3. 我预测错了：按段落切**不是**最差的

ADR-001 里我根据"段落中位长度只有 28 字符、82% 不足 100 字符"判断：
按段落切会切出大量碎片，检索会明显变差，所以选了"按标题分节"。

**实测推翻了预测**（新评估集，sparse 通道）：

| 策略 | recall@5 | MRR | hit@1 |
|---|---|---|---|
| paragraph | 0.7885 | **0.6490** | **0.5577** ← 两个都最高 |
| heading | **0.9038** | 0.6478 | 0.5000 |

- recall 上 heading 明显更好（0.90 vs 0.79）—— **这部分预测对了**
- 但 **MRR 与 hit@1 上 paragraph 都最高**：小块更聚焦，命中时排得更靠前

所以准确的说法是：**段落切牺牲召回，换来更好的排序质量**。
两者是权衡，不是"一个对一个错"。

这个案例值得记住：**参数决策要先用评估集验证，别信直觉** ——
我当初的判断有一半是错的，而且是"看起来很合理"的那种错。

### 4. 重排：**明显优于 RRF 融合，但仍然打不过纯 sparse**

先做分段诊断确认瓶颈在哪（`eval/diagnose_rerank.py`，新评估集）：

```
召回段（gold 有没有进候选池）:
  sparse        recall@50 = 1.0000
  dense         recall@50 = 0.9231
  union(50+50)  recall@池 = 1.0000     ← 比任何单路都好
```

> **这段的合并策略踩了三个坑**（细节在 ADR-007）：
>
> 1. **拼接**（先 dense 全部、再 sparse 全部）→ dense 的重复项先占名额，
>    sparse 独有的候选被挤掉：`recall@50` 只有 0.9615
> 2. **交错合并** → sparse 的**尾部**落到第 50 位之后：0.9808
> 3. **加大 recall_k** → 对最终指标毫无影响（50→200 完全一样）
>
> **想明白的事**：既然 RRF 融合已被否定（ADR-004），两路就不该竞争同一批名额。
> 池子 = 两路召回结果的**完整并集**，不设"取前 N 个"截断。
> 多算几次便宜的词法打分，换"一路找到的东西一个都不丢"——
> 因为**漏掉 gold 是无法补救的**。

重排后的结果（新评估集）：

| | recall@5 | MRR | hit@1 |
|---|---|---|---|
| hybrid（RRF 融合两路） | 0.7308 | 0.4821 | 0.3077 |
| **rerank（union + 词法重排）** | 0.8462 | **0.6385** | **0.5000** |
| 相对 hybrid 提升 | +0.115 | +0.156 | +0.192 |
| 对比 sparse 基线 | −0.058 | −0.009 | **±0.000** |

**结论要说清楚**：重排相对 RRF 融合是压倒性改善，但**打不过"只用 sparse"**。

原因还是那个根本局限：**词法重排和稀疏用的是同一类信息**，
没有新增语义信号。想超过它只能靠**语义信息** —— 也就是换 embedding。

（注：这句话在评估集改造前写的是"稀疏已经是天花板、recall@5 = 1.0"。
**那个"1.0"是评估集太容易造成的假象** —— 加入 44% 改写问句后掉到 0.9038。
详见下面的第 6 条。）

### 5. 我的"邻近度"信号方向反了（一个真实的度量设计错误）

我给重排加了三个信号，其中"查询词邻近度"的实现是：

```python
coverage = (最大命中位置 - 最小命中位置) / len(doc)
score = 1.0 - coverage          # ❌ 用文档长度当分母
```

网格扫描显示**它在任何组合下都是负作用**（新评估集上同样成立）：

| heading | recall@5 (prox=0) | recall@5 (prox=0.2) |
|---|---|---|
| 0.0 | **0.8654** | 0.7308 |
| 0.3 | **0.8462** | 0.7115 |
| 0.8 | **0.7885** | 0.6923 |

**根因**：用文档长度归一化，于是
- **长而不相关的块**：查询词恰好落在相邻位置 → 得分高
- **短而精准的 gold 块**：查询词分布在整个块里 → 得分低

它**系统性地奖励长的噪音块、惩罚短的正确答案**。已把默认权重设为 0。

**顺带修的第二个错**：扫描过程中发现改了 dataclass 默认值但指标不变 ——
因为 CLI 的 `--w-proximity` 默认值（0.3）**覆盖**了它。
已改成 CLI 默认值从 `RerankWeights()` 取，**默认值只留一个来源**。

### 6. 评估集本身有问题：**旧的 30 条太容易，掩盖了真实水平**

补题时做了个审计（`eval/audit_questions.py`）：算每条题的查询 n-gram
有多大比例出现在 gold 文档里。结果：

| 分桶 | 改造前 | 改造后 |
|---|---|---|
| 字面重合（≥0.55） | 14 条（**53.8%**） | 14 条（26.9%） |
| 部分改写（0.35~0.55） | 9 条（34.6%） | 15 条（28.8%） |
| **改写问句（<0.35）** | **3 条（11.5%）** | **23 条（44.2%）** |

**问题**：原评估集的题面用词与文档高度重合 ——
问"flush"文档里就写着 flush，问"BOM"文档里就写着 BOM。
**词法检索当然满分。那不是检索好，是题太容易。**

补了 `q031~q056`，其中 `q031~q048` 刻意改写，例如：

| 题面 | gold 文档里的原词 |
|---|---|
| 前端界面是怎么分发的，为什么没有引入打包工具？ | "Vue 3 走 CDN" |
| 服务端保存了对话上下文吗？ | "完全无状态" |
| 验收时为什么要启动一个真实的服务器进程？ | "真进程 + 真 HTTP" |
| 用户来源字段存在什么数据质量问题？ | "渠道名大小写不一" |

**改造后所有指标都下降 —— 但那才是真实水平**：

| 通道 | 旧 30 条 | 新 56 条 | 变化 |
|---|---|---|---|
| dense | 0.6538 | 0.4615 | **−0.192** |
| **sparse** | **1.0000** | **0.9038** | **−0.096** |
| hybrid | 0.7692 | 0.7308 | −0.038 |
| rerank | 0.9231 | 0.8462 | −0.077 |

> **这件事的意义比数字本身大**：一个"所有方法都接近满分"的评估集
> 是没有诊断能力的 —— 它既不能暴露方案的短板，也无法衡量改进。
> 而且这也说明 **ADR-002 关于"词法方案弱在改写问句"的判断是对的**，
> 只是旧评估集几乎不含这类题，把问题完全掩盖了。

**顺带修正的两个测量错误**（都会导致去修一个不存在的问题）：

| 错误 | 现象 | 正确做法 |
|---|---|---|
| 用"位置名次"衡量 union 的召回 | union recall@50 = 0.9808 < sparse 1.0，像是合并坏了 | union 池子比 k 大，"名次"只是展示顺序。**只看 gold 在不在池里** → 实测 1.0000 |
| 写死"1 条题值多少" | 脚本印着"26 条题，1 条 = 0.0385" | 扩到 52 条后 1 条只值 **0.0192**，判断门槛整个错位。改成动态计算 |

### 7. 补上语义信号后，**hit@1 从 0.50 跳到 0.79**

前面几条已经把问题定位得很清楚了：

- 第 1 条：稠密检索"找得到但排不好"，瓶颈是**排序**
- 第 4 条：**词法重排打不过纯 sparse** —— 因为它和稀疏用的是**同一类信息**
- 第 6 条：评估集加入 44% 改写问句后，sparse 掉的**全是"换了说法"的题**

**所以推论很清楚：缺的是语义信号。** 用 LLM 做重排来验证：

| 指标 | sparse | **llm 重排** | 提升 |
|---|---|---|---|
| recall@5 | 0.9038 | **0.9808** | **+0.077** |
| MRR | 0.6478 | **0.8638** | **+0.216（+33%）** |
| hit@1 | 0.5000 | **0.7885** | **+0.288（+58%）** |

**推论被完全验证。** 而且要注意对比：词法重排（第 4 条）在同样的两段式框架下
**打不过** sparse；换成 LLM 打分，**同样的召回、同样的框架**，指标全面反超。

> **这个对照实验才是重点**：变化只有一个变量（打分方式：词法 → 语义），
> 结果却是从"输给基线"变成"大幅超越基线"。
> 这说明**前面的失败不是框架问题，是信号问题** ——
> 如果没做第 4 条那个"失败的词法重排"，就拿不到这个清晰结论。

**但代价必须说清楚**：**2873 秒 vs 0.3 秒，约 11000 倍。**

### 8. 给 LLM 太多候选**反而更差**

用缓存的打分重算成本曲线（**零 API 调用**）：

| 候选上限 | recall@5 | MRR | hit@1 | vs全池成本 |
|---|---|---|---|---|
| 15 | 0.9423 | **0.8606** | **0.8077** | **17%** |
| 50 | 0.9423 | 0.8510 | 0.7885 | 58% |
| 95（全池） | **0.9808** | 0.8638 | 0.7885 | 100% |

**15 → 95 是 5.7 倍成本，换来 MRR +0.003（约 0.15 条题）。**
而且 **hit@1 反而下降**（0.8077 → 0.7885）——
候选太多时，噪音把正确答案挤下去了。

> 实践建议：日常用 `--llm-max-candidates 15`（成本 17%、hit@1 最高）；
> 只有"recall 绝对优先"时才上全池。

```powershell
# 3. 端到端冒烟：建索引 + 三通道检索，人工看结果
& $py smoke_retrieve.py

# 4. 先校验评估集本身（gold_doc 真的存在吗？）
& $py eval\check_questions.py

# 5. 算指标（核心产出）——含重排对比
& $py eval\run_eval.py --strategy heading --k 5 --rerank `
       --modes dense,sparse,hybrid,rerank --verbose

# 6. 分段诊断：如果重排不好，问题在召回段还是重排段？
& $py eval\diagnose_rerank.py

# 7. 调词法重排权重（**用扫描而不是手调**）
& $py eval\sweep_rerank.py

# 8. LLM 语义重排（需要 .env 里的 DEEPSEEK_API_KEY，见下）
#    先小规模验证，再上全量 —— 全量一次是上千次 API 调用
& $py eval\make_subset.py 5
& $py eval\run_eval.py --questions eval\_subset.jsonl --strategy heading `
       --llm-rerank --modes sparse,llm
#    全量（约 48 分钟，但结果会缓存，重跑几乎瞬间完成）
& $py eval\run_eval.py --strategy heading --k 5 --llm-rerank --modes sparse,llm
#    想省钱就限制候选数：15 个即饱和（成本 17%，hit@1 反而更高）
& $py eval\run_eval.py --strategy heading --llm-rerank --llm-max-candidates 15 `
       --modes sparse,llm
#    成本/效果曲线（用已缓存打分重算，零 API 调用）
& $py eval\sweep_llm_candidates.py

# 9. 带门禁（可用在 CI）
& $py eval\run_eval.py --strategy heading --fail-under "recall@5=0.85"
```

### 关于 API Key

LLM 重排需要 DeepSeek 的 Key（**它不提供 embedding 端点**，实测 404，
所以只能用于重排与生成）。放到 `ai-lab/projects/project2-rag/.env`：

```
DEEPSEEK_API_KEY=sk-...
OPENAI_BASE_URL=https://api.deepseek.com/v1
```

`.env` 已被 `.gitignore` 覆盖（验证过 `git check-ignore`）。
`rag/llm_rerank.py` 会**自动读取** `.env`，不用手动 export。

> ⚠️ 两个实测踩到的参数坑（详见 ADR-009）：
> `deepseek-flash` 与 `deepseek-v4-pro` **都是推理模型** ——
> 先输出 `reasoning_content`（思维链），`content`（答案）在后面。
> 所以 `max_tokens` 给小了（比如 4）**会永远拿到空内容**，
> 看起来像"调用失败"。默认已给 1500。

> **装依赖务必加 `--only-binary :all:`**：本机没有 C 编译器，
> 不加这个参数 pip 会尝试源码构建，卡在 CPU 上空转（实测烧 301 秒还没完，
> 看起来像网速慢）。加了之后 numpy 14 秒装完。详见 [windows-quickstart](../../docs/windows-quickstart.md)。

## 面试能讲什么（这个项目的价值在这）

| 面试问题 | 你能给的答案 |
|---|---|
| 你的检索准不准？ | recall@5 / MRR / hit@1 具体数字，**五个通道**对比 |
| 切块怎么定的？ | 三种策略**用同一评估集对比**，并说出"段落切牺牲召回换排序"这个权衡 |
| 混合检索一定更好吗？ | **不一定** —— 实测 hybrid 低于纯稀疏，原因是 RRF 被弱通道拖累，有公式解释 |
| 重排有用吗？ | **两个重排，一败一成**：词法重排打不过纯稀疏（缺语义信号）；LLM 重排 hit@1 从 0.50 提到 0.79。**关键是对照实验只变了一个变量** |
| 为什么不用 embedding 提升语义？ | 实测 DeepSeek **没有 /embeddings 端点**（404）。所以语义能力走重排这条路 |
| 怎么控制成本？ | 扫出成本曲线：**15 个候选就饱和**，15→95 是 5.7 倍钱换 MRR +0.003，且 hit@1 反而降 |
| 怎么调参的？ | **网格扫描而不是手调**；且明确指出"52 条题里 1 条 = 0.0192"，小于这个的差异不算改进 |
| 怎么知道优化有效？ | 评估集 + 门禁脚本；改动前后指标可复现；长任务有缓存可重放 |
| 你踩过什么坑？ | 见下面那张表 —— 里面有**好几个是我自己设计错了** |

### 我的设计错误（这部分比成功案例更能说明工程能力）

| 错误 | 症状 | 根因 |
|---|---|---|
| **邻近度信号方向反了** | 加了它所有指标变差 | 用 `len(doc)` 当分母 → **奖励长的噪音块、惩罚短的正确答案**。已默认关闭并记录对照数据 |
| **union 合并改了三版** | sparse 单独 recall@50=1.0，union 只有 0.96 / 0.98 | ① 拼接让重复项挤占名额 ② 交错让 sparse 尾部出局。最终改成"完整并集、不设截断" |
| **用错口径量 union 召回** | union 0.9808 < sparse 1.0，像是合并坏了 | union 池子比 k 大，"名次"只是展示顺序。**只看 gold 在不在池里** → 1.0000 |
| **默认值有两处来源** | 改了 dataclass 默认值但指标不变 | CLI 的 `--w-proximity` 默认值**覆盖**了它，白跑几轮才定位 |
| **把 API 失败静默成 0 分** | 36 次调用失败 35 次，现象像"LLM 重排无效" | `except: score = 0.0`。**把失败伪装成数据比崩掉更危险** —— 一次都没成功，却像方法没效果 |
| **长任务没有进度可看** | 跑了 20 分钟缓存不更新，我误判成卡死把它杀了 | 结果攒在内存里，**前面花钱买的打分全丢**。改成每 50 次落一次盘 |
| **推理模型 max_tokens 给小** | `content` 永远是空，误判成"网络失败 35/36 次" | 两个模型都是推理模型：先写 `reasoning_content` 再给答案。4 个 token 连思维链都写不完 |
| **验证路径和生产不一致** | smoke 测试通过，全量评估失败 | smoke 走逐条调用，生产走批量。**验证必须走生产路径**，否则没有意义 |
| **切块策略预测错了一半** | ADR-001 说按段落切会很差 | 实测 recall 确实略低，但 **MRR/hit@1 反而最高** —— 同一份统计数据能推出相反结论 |
| **FTS5 中文不可用** | `函数` 命中 0 条 | unicode61 按整块切；trigram 又要求 ≥3 字符，2 字词依然失败 → 自建倒排 |
| **pip 源码构建空转** | 装 numpy 烧 301 秒 CPU | 本机无 C 编译器，pip 在尝试构建源码。加 `--only-binary :all:` 后 14 秒 |
| **`.pytest_cache` 混入语料** | 缓存说明文件被当知识库文档 | 排除清单漏了构建/缓存产物目录 |
