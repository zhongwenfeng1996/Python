## ADR-001 · 切块策略：按标题分节 + 节内合并，不按段落切

**状态**：已采纳
**日期**：2026-10

### 背景

切块大小是 RAG 里最容易被拍脑袋决定的参数，也是最容易背锅的——
检索效果差的时候，你根本不知道是"检索算法不行"还是"块切得不对"。

所以先量了语料的真实形态（`probe_corpus.py`，结果可复现）：

| 指标 | 实测值 |
|---|---|
| 语料规模 | 18 个 Markdown，121,877 字符 |
| 正文 | 59,483 字符 / 915 段 |
| **代码块占比** | **49.3%**（60,095 字符 / 245 段） |
| 段落中位长度 | **28 字符** |
| 段落平均长度 | 65 字符 |
| **不足 100 字符的段落** | **751 / 915（82%）** |
| 标题数量 | 206 个 `#`、128 个 `##`、70 个 `###` |
| 超过 1000 字符的长段 | 2 个 |

### 决策

**三段式切块：**

1. **按标题分节**（`#`~`###`）—— 每个块带上所属标题路径
2. **节内按段落累积**，到阈值（约 600 字符）就封块
3. **代码块不可切断** —— 以代码块为硬边界；超长节按目标大小二次切分，
   并在块间留约 80 字符重叠（overlap）避免语义断裂

**每个块带上元数据**：`source_path`、`heading_path`、`chunk_index`。
检索结果要能给出"来自哪个文件的哪一节"，这是引用功能的前提。

### 备选方案与为什么不选

| 方案 | 为什么不选 |
|---|---|
| **每个段落一个块** | ❌ **实测否决**：82% 的段落不足 100 字符。会切出 700+ 个「没头没尾」的碎片，检索出来无法判断相关性 |
| **固定字符数硬切**（如每 500 字符） | ❌ 会切断代码块和句子；且丢失标题上下文 |
| **按 token 数切** | ⚠️ 更贴近模型限制，但**本地没有 tokenizer**（无 Key、tiktoken 未装）。先用字符数近似；接入真实模型后再换成 token 数 |
| **句级切分** | ❌ 中文句号切分对 Markdown 列表/表格失效；且平均 65 字符太碎 |

### 影响

- 块数量预计 200~300（而不是 915+），每个块自带标题上下文
- `chunk_size` / `overlap` 是**可配置参数**，后续用同一套评估集对比不同取值（见 ADR-005）

### ⚠️ 实测结果：我的判断被推翻了一半（2026-10 补充）

三种策略用同一套评估集（30 条）跑出来的结果：

| 策略 | 块数 | sparse recall@5 | sparse MRR |
|---|---|---|---|
| `fixed` | 351 | 0.9615 | 0.6840 |
| `paragraph` | 1344 | 0.9231 | **0.7917** |
| `heading`（本文决策） | 488 | **1.0000** | 0.7558 |

**预测对的部分**：`paragraph` 的 recall 确实更低（0.9231 < 1.0000）——
碎片化确实损失了召回，这部分判断成立。

**预测错的部分**：**MRR 上 `paragraph` 反而最高（0.7917 > 0.7558）**。
我原以为"碎片 = 差"，但实测显示：小且聚焦的块**命中时排得更靠前**。
精确段落比"包含多个话题的长块"在排序上更有优势。

**准确的结论应该是**：

> `heading` 与 `paragraph` 是**权衡关系**，不是对错关系 ——
> 段落切牺牲一点召回，换来更好的排序质量。
> 选哪个取决于下游更在意"别漏"（recall）还是"别把不相关的塞进 prompt"（排序）。

**当前仍保持 `heading` 为默认**，理由：
1. `heading` 的 recall 是 1.0 —— 在 RAG 里漏掉正确答案的代价更大
   （模型没拿到资料就一定答错，而排序差只是 prompt 里多几条噪音）
2. 块自带标题路径，便于生成引用
3. 块数少 3 倍（488 vs 1344），索引与检索成本更低

**但这条决策的优先级降低了**：既然差距在 0.03 的 MRR 量级，
说明它**不是**当前最大的瓶颈 —— 瓶颈是 embedding（见 ADR-002 的实测补充）。

**这个案例的教训（值得单独记住）**：

> 参数决策要先用评估集验证，**别信直觉**。
> 我当初的判断有一半是错的，而且是"看起来很合理"的那种错 ——
> 因为"数据支持"和"数据推翻"都可能从同一份统计数据里读出来。
> 28 字符的中位段落长度 → 既可以推出"会碎片化所以差"，
> 也可以推出"短而聚焦所以排得准"。**只有跑指标能分辨。**

## ADR-002 · Embedding：统一接口 + 两种实现（本地确定性 / 真实 API）

**状态**：已采纳
**日期**：2026-10

### 背景

RAG 的检索质量**主要由 embedding 决定**。但当前本机：

- ❌ 没有任何 API Key（`.env` 不存在）
- ❌ 本机是**国内网络**，OpenAI 不可达
- ⚠️ 本地跑 `sentence-transformers` 需要 torch（~200MB）+ 模型文件（~400MB），
  且 HuggingFace 在本机不一定可达

如果卡在"等一个能用的 embedding"，整个项目就没法开始，
更糟的是**评估做不了**——而评估才是这个项目的核心价值。

### 决策

**定义一个 `Embedder` 接口，提供两种实现，可一键切换：**

| 实现 | 用途 | 特点 |
|---|---|---|
| `LocalHashEmbedder`（默认） | 开发、测试、CI、离线评估 | 字符 n-gram → 哈希到固定维度 → L2 归一化。**确定性、零成本、零网络** |
| `APIEmbedder` | 真实效果、最终基线 | 走 OpenAI 兼容端点（bge-m3 / text-embedding-3）。需 Key |

默认走本地实现，**保证今天就能把全链路跑通并量化**；填了 Key 自动切换。

### 为什么"本地确定性 embedding"不是凑数

绝大多数做法是"随便返回随机向量"或"直接用词频"——那都不可复现或不适合语义检索。
字符 n-gram 哈希的做法：

- **对中文友好**：按 2~3 字符滑窗提取，中文没有空格也能切
- **有局部性**：字符重叠多的文本向量更接近 —— 这正是我们要的"字面相似"
- **完全确定**：同一输入永远同向量 → 评估结果可复现、可写进 CI

它的**已知短板**（必须写清楚，否则评估结果会被误读）：
语义泛化弱 —— 同义词、改写问句的召回会明显差于真实 embedding。
**这正是它的价值**：它给出一个"下限基线"，等你接入真实模型，
recall 的提升幅度就是可量化的收益。

### 备选方案与为什么不选

| 方案 | 为什么不选 |
|---|---|
| **只用真实 API embedding** | ❌ 没 Key；且每次评估都花钱、依赖网络，CI 跑不了 |
| **本地 sentence-transformers** | ⚠️ 最理想（真语义 + 离线），但需 torch + 模型下载。**留作后续升级路径**，不是当前阻塞项 |
| **降级成纯 BM25 关键词检索** | ❌ 那就不是"向量检索"了，学不到 embedding 选型与维度概念 |
| **随机向量** | ❌ 不可复现，评估结果无意义 |

### 影响

- 检索质量会有**两个数字**：本地基线、真实模型基线。两者对比本身就是简历素材
- 存储层必须记录用的是哪个 embedder（维度可能不同）—— 换模型要重建索引

### ⚠️ 实测结果：短板被精确量化了（2026-10 补充）

当初写的是定性判断"语义泛化弱"。用 30 条评估集跑完，它变成了具体数字：

| k | dense recall | dense MRR |
|---|---|---|
| 1 | 0.3462 | 0.3462 |
| 5 | 0.6538 | 0.4545 |
| 20 | 0.8462 | 0.4694 |
| 50 | 0.9615 | 0.4721 |
| 100 | **1.0000** | 0.4726 |

**读法**：recall@100 = 100% 说明**它从不"找不到"**（26 个目标全部在候选里），
但 MRR 从 0.4545 到 0.4726 几乎不涨 —— 说明**它排不好**，
把大量不相关块放在了前面。

原因具体到机制：评估集里很多问题是**改写问句**
（问"为什么日志要用 flush handler"，文档里写的是"块缓冲"），
字符 n-gram 只认字面重叠，这种问句自然排不到前面。

### 由此得到的最重要一条结论

> **想在 RAG 上拿到好看的数字，换 embedding 比调检索算法有效得多。**

这条结论只有先跑出基线才说得出来。它直接决定了后续的投入顺序：
先解决 embedding（需要 API Key 或本地模型），再谈 rerank、混合权重这些细节。

**这也是"下限基线"设计的价值**：如果一开始就用真实模型，
你只会看到一个还不错的数字，**永远不知道算法本身贡献了多少**。

## ADR-003 · 检索层可替换：存储与模型都不锁死

**状态**：已采纳
**日期**：2026-10

### 背景

学习计划第 5 周要求 **pgvector**（含 `ivfflat` / `hnsw` 索引）。
但本机**当前跑不了 Docker**：

| 阻碍 | 状态 |
|---|---|
| CPU 虚拟化（AMD Ryzen 3700X 的 SVM Mode） | ❌ BIOS 里未开启 |
| Windows 版本 | 10 **1903**（Build 18362）；Docker Desktop 要求 22H2（19045+） |
| WSL2 / Hyper-V | 全部 Disabled |
| `registry-1.docker.io` | ❌ 不可达（需配镜像加速器） |

### 决策

**把存储层做成接口，先实现一个不依赖 Docker 的后端，Docker 就绪后新增 pgvector 后端。**

分阶段：

| 阶段 | 向量存储 | 检索方式 | 能学到什么 |
|---|---|---|---|
| **P1（当前）** | SQLite（向量存 BLOB） | numpy 暴力算余弦 | 检索原理、指标口径、切块影响 |
| **P2** | SQLite + `sqlite-vec` 扩展 | 原生向量索引 | **有索引 vs 无索引**的速度/精度差异 |
| **P3（Docker 就绪）** | PostgreSQL + pgvector | `ivfflat` / `hnsw` | 生产级方案、索引参数调优 |

### 为什么这不是"妥协"

面试时 **"我用过两种实现，知道各自的边界"** 比 **"我只用过 pgvector"** 更有说服力：

- P1 的暴力检索在几百条文档下完全够用 —— 你会**亲身体会到"够用"的边界在哪**
- P2/P3 引入索引后，能给出**具体的加速倍数与 recall 损失**（`ivfflat` 是近似索引，会掉召回）
- 换存储层时检索接口不变 —— 这本身就是"依赖倒置"的实践

### 风险与缓解

- ⚠️ **风险**：如果一直不开 BIOS，就学不到 pgvector。
  **缓解**：BIOS 开启 + 系统升级是独立的小任务，不阻塞 P1/P2。
  而且计划要求 Docker，早晚要做 —— 越早越好。

## ADR-004 · 检索策略：稠密 + 稀疏 + RRF 混合，三者可对比

**状态**：已采纳
**日期**：2026-10

### 背景

纯向量检索有明确的失效场景（计划第 5 周也点名了）：
否定词、专有名词、长查询、跨语言。而纯关键词检索又无法处理同义改写。

实测还发现一个**中文特有的坑**（`probe_env.py`）：

```
SQLite FTS5 默认分词器（unicode61）:
  查询 '函数'    -> 命中 0
  查询 '作用域'  -> 命中 0
  查询 'def'     -> 命中 1

trigram 分词器:
  查询 '作用域'  -> 命中 1
  查询 '函数'    -> 命中 0     ← 2 字查询仍然失败！
```

**trigram 分词器要求查询至少 3 个字符**，而中文里 2 字关键词
（向量、切片、函数、召回、降级）极其常见 —— **这个限制不能接受**。

### 决策

**三通道，且都要能单独跑、用同一套评估集对比：**

| 通道 | 实现 | 定位 |
|---|---|---|
| **稠密** | 本地 n-gram 向量 + 余弦 | 主力。中文友好、能抓改写 |
| **稀疏** | **自建字符 n-gram 倒排索引**（不用 FTS5） | 补精确匹配；2 字词也能命中 |
| **混合** | **RRF（Reciprocal Rank Fusion）** 融合两路排名 | 通常最优；RRF 简单、不需要调权重 |

**为什么自建倒排而不用 FTS5**：FTS5 的 unicode61 对中文按整块切（几乎不可用），
trigram 又不支持 2 字查询。而我们在做 embedding 时**本来就要提取字符 n-gram** ——
顺手建倒排，成本几乎为零，且完全可控。

### RRF 为什么优于加权求和

```
RRF(d) = Σ  1 / (k + rank_i(d))        k 通常取 60
```

- **不需要归一化**：稠密是余弦相似度（0~1），稀疏是 BM25 分数（无上界），
  量纲不同，加权求和必须调权重 + 归一化，很脆弱
- **只看排名**：对分数尺度不敏感，鲁棒
- **一个参数**（k），且有成熟默认值

### 影响

- 评估必须**分别报告三个通道的 recall@5 / MRR** —— 这组对比表就是项目的核心产出
- 混合检索不总是最好：如果稠密已经很差，融合也救不回来，要如实报告

### ⚠️ 实测结果：混合**确实**更差，而且能算出来为什么（2026-10 补充）

| 通道 | recall@5 | MRR | hit@1 |
|---|---|---|---|
| dense | 0.6538 | 0.4545 | 0.3462 |
| **sparse** | **1.0000** | **0.7558** | **0.6154** |
| hybrid（RRF） | 0.7692 | 0.5942 | 0.4615 |

直觉是"混合一定比单一好"。**实测 hybrid 低于纯 sparse。**
ADR-004 里我写的是"混合通常最优"，这个预判**被推翻了**。

原因在 RRF 的公式本身：

```
RRF(d) = Σ 1/(k + rank_i(d))        k = 60
```

关键：用的是**排名**不是分数。两路各取 pool=30 个候选，于是：

- sparse 排第 1 的块 → `1/61 ≈ 0.0164`
- **dense 排第 1 的块（可能完全不相关）→ 也是 `1/61 ≈ 0.0164`**

dense 的 30 个候选里即使大多不相关，也每个都拿到 `1/61 ~ 1/90` 的分。
稀疏的排名本来是准的，但候选池被稠密塞进了 30 个"排名靠前却不对"的块，
融合后真正的好结果被挤到后面。

**教训**：

> 混合检索的前提是**两路都别太差**。一路明显弱时，融合只会拉低整体。
> 正确做法是先提升弱通道（换 embedding，见 ADR-002 的实测补充），
> 或者给弱通道降权 —— 但降权必须有数据支撑，不能凭感觉调。

**一个反直觉的推论**：RRF "对分数尺度不敏感"是它的优点，
但在**某一路整体失准**时，这个优点就变成了缺点 ——
因为它无法识别"这一路的第一名其实很垃圾"。
加权求和反而能通过权重压制弱通道（前提是你知道该给多少）。

## ADR-005 · 评估集：50 条以上，必须可复现、可门禁

**状态**：已采纳
**日期**：2026-10

### 背景

学习计划明确写了：**"建 50 条评估集（这一步决定了你后面所有优化是否有意义）"**，
以及"基线纯向量检索 recall@5 有明确数值记录（通常 0.5–0.7），不靠感觉"。

没有评估集，RAG 就只能靠"试几个问题看看"——那不是工程，是玄学。

### 决策

**评估集格式**（`eval/questions.jsonl`，一行一条）：

```json
{"id": "q001", "question": "章节重排后 def 在第几章教？",
 "answer": "第 04 章", "gold_doc": "python_basics/docs/04-函数.md",
 "type": "fact", "difficulty": "easy"}
```

**硬性要求：**

1. **≥ 50 条**，覆盖多种类型：事实查找、跨段推理、代码相关、**不可答（应拒答）**
2. **gold_doc 必须真实存在**并在脚本里校验 —— 否则指标算的是错的东西
3. **指标可复现**：同一个 embedder + 同一个索引 → 指标每次一样
4. **带门禁**：`--fail-under recall@5=0.6`，指标掉了就返回非 0（可用于 CI）

**指标定义（写清口径，避免自欺）：**

| 指标 | 定义 |
|---|---|
| `recall@k` | 前 k 个结果里**包含 gold_doc 的查询比例**。分母是**所有查询**（含不可答的？—— 不含，不可答题单独算） |
| `MRR` | 第一个命中结果的排名倒数的平均。**比 recall@k 更敏感**：命中了但排第 5 vs 排第 1，这里能区分开 |
| `拒答准确率` | 不可答题里，系统正确拒答的比例（避免"什么都敢答"） |

### 关于 50 条怎么来（诚实说明）

题必须是**有真实答案的**，不能编。做法：

- 语料是仓库自己的文档，内容我完全掌握 → 可以基于文档事实出题
- 每条题必标注 `gold_doc`，并在生成脚本里**校验该文件存在**
- 主观题（"这段代码好吗"）不入评估集 —— 无法机械判定

**这一步不能省、也不能糊弄。** 评估集造假 = 后面所有指标都没有意义。
