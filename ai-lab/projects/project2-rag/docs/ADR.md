## ADR-001 · 切块策略：按标题分节 + 节内合并，不按段落切

**状态**：已采纳
**日期**：2026-10

### 背景

切块大小是 RAG 里最容易被拍脑袋决定的参数，也是最容易背锅的——
检索效果差的时候，你根本不知道是"检索算法不行"还是"块切得不对"。

所以先量了语料的真实形态（`probe_corpus.py`，结果可复现）：

| 指标 | 实测值 |
|---|---|
| 语料规模 | 18 个 Markdown，121,877 字符 |
| 正文 | 59,483 字符 / 915 段 |
| **代码块占比** | **49.3%**（60,095 字符 / 245 段） |
| 段落中位长度 | **28 字符** |
| 段落平均长度 | 65 字符 |
| **不足 100 字符的段落** | **751 / 915（82%）** |
| 标题数量 | 206 个 `#`、128 个 `##`、70 个 `###` |
| 超过 1000 字符的长段 | 2 个 |

### 决策

**三段式切块：**

1. **按标题分节**（`#`~`###`）—— 每个块带上所属标题路径
2. **节内按段落累积**，到阈值（约 600 字符）就封块
3. **代码块不可切断** —— 以代码块为硬边界；超长节按目标大小二次切分，
   并在块间留约 80 字符重叠（overlap）避免语义断裂

**每个块带上元数据**：`source_path`、`heading_path`、`chunk_index`。
检索结果要能给出"来自哪个文件的哪一节"，这是引用功能的前提。

### 备选方案与为什么不选

| 方案 | 为什么不选 |
|---|---|
| **每个段落一个块** | ❌ **实测否决**：82% 的段落不足 100 字符。会切出 700+ 个「没头没尾」的碎片，检索出来无法判断相关性 |
| **固定字符数硬切**（如每 500 字符） | ❌ 会切断代码块和句子；且丢失标题上下文 |
| **按 token 数切** | ⚠️ 更贴近模型限制，但**本地没有 tokenizer**（无 Key、tiktoken 未装）。先用字符数近似；接入真实模型后再换成 token 数 |
| **句级切分** | ❌ 中文句号切分对 Markdown 列表/表格失效；且平均 65 字符太碎 |

### 影响

- 块数量预计 200~300（而不是 915+），每个块自带标题上下文
- `chunk_size` / `overlap` 是**可配置参数**，后续用同一套评估集对比不同取值（见 ADR-005）

### ⚠️ 实测结果：我的判断被推翻了一半（2026-10 补充）

三种策略用同一套评估集（30 条）跑出来的结果：

| 策略 | 块数 | sparse recall@5 | sparse MRR |
|---|---|---|---|
| `fixed` | 351 | 0.9615 | 0.6840 |
| `paragraph` | 1344 | 0.9231 | **0.7917** |
| `heading`（本文决策） | 488 | **1.0000** | 0.7558 |

**预测对的部分**：`paragraph` 的 recall 确实更低（0.9231 < 1.0000）——
碎片化确实损失了召回，这部分判断成立。

**预测错的部分**：**MRR 上 `paragraph` 反而最高（0.7917 > 0.7558）**。
我原以为"碎片 = 差"，但实测显示：小且聚焦的块**命中时排得更靠前**。
精确段落比"包含多个话题的长块"在排序上更有优势。

**准确的结论应该是**：

> `heading` 与 `paragraph` 是**权衡关系**，不是对错关系 ——
> 段落切牺牲一点召回，换来更好的排序质量。
> 选哪个取决于下游更在意"别漏"（recall）还是"别把不相关的塞进 prompt"（排序）。

**当前仍保持 `heading` 为默认**，理由：
1. `heading` 的 recall 是 1.0 —— 在 RAG 里漏掉正确答案的代价更大
   （模型没拿到资料就一定答错，而排序差只是 prompt 里多几条噪音）
2. 块自带标题路径，便于生成引用
3. 块数少 3 倍（488 vs 1344），索引与检索成本更低

**但这条决策的优先级降低了**：既然差距在 0.03 的 MRR 量级，
说明它**不是**当前最大的瓶颈 —— 瓶颈是 embedding（见 ADR-002 的实测补充）。

**这个案例的教训（值得单独记住）**：

> 参数决策要先用评估集验证，**别信直觉**。
> 我当初的判断有一半是错的，而且是"看起来很合理"的那种错 ——
> 因为"数据支持"和"数据推翻"都可能从同一份统计数据里读出来。
> 28 字符的中位段落长度 → 既可以推出"会碎片化所以差"，
> 也可以推出"短而聚焦所以排得准"。**只有跑指标能分辨。**

## ADR-002 · Embedding：统一接口 + 两种实现（本地确定性 / 真实 API）

**状态**：已采纳
**日期**：2026-10

### 背景

RAG 的检索质量**主要由 embedding 决定**。但当前本机：

- ❌ 没有任何 API Key（`.env` 不存在）
- ❌ 本机是**国内网络**，OpenAI 不可达
- ⚠️ 本地跑 `sentence-transformers` 需要 torch（~200MB）+ 模型文件（~400MB），
  且 HuggingFace 在本机不一定可达

如果卡在"等一个能用的 embedding"，整个项目就没法开始，
更糟的是**评估做不了**——而评估才是这个项目的核心价值。

### 决策

**定义一个 `Embedder` 接口，提供两种实现，可一键切换：**

| 实现 | 用途 | 特点 |
|---|---|---|
| `LocalHashEmbedder`（默认） | 开发、测试、CI、离线评估 | 字符 n-gram → 哈希到固定维度 → L2 归一化。**确定性、零成本、零网络** |
| `APIEmbedder` | 真实效果、最终基线 | 走 OpenAI 兼容端点（bge-m3 / text-embedding-3）。需 Key |

默认走本地实现，**保证今天就能把全链路跑通并量化**；填了 Key 自动切换。

### 为什么"本地确定性 embedding"不是凑数

绝大多数做法是"随便返回随机向量"或"直接用词频"——那都不可复现或不适合语义检索。
字符 n-gram 哈希的做法：

- **对中文友好**：按 2~3 字符滑窗提取，中文没有空格也能切
- **有局部性**：字符重叠多的文本向量更接近 —— 这正是我们要的"字面相似"
- **完全确定**：同一输入永远同向量 → 评估结果可复现、可写进 CI

它的**已知短板**（必须写清楚，否则评估结果会被误读）：
语义泛化弱 —— 同义词、改写问句的召回会明显差于真实 embedding。
**这正是它的价值**：它给出一个"下限基线"，等你接入真实模型，
recall 的提升幅度就是可量化的收益。

### 备选方案与为什么不选

| 方案 | 为什么不选 |
|---|---|
| **只用真实 API embedding** | ❌ 没 Key；且每次评估都花钱、依赖网络，CI 跑不了 |
| **本地 sentence-transformers** | ⚠️ 最理想（真语义 + 离线），但需 torch + 模型下载。**留作后续升级路径**，不是当前阻塞项 |
| **降级成纯 BM25 关键词检索** | ❌ 那就不是"向量检索"了，学不到 embedding 选型与维度概念 |
| **随机向量** | ❌ 不可复现，评估结果无意义 |

### 影响

- 检索质量会有**两个数字**：本地基线、真实模型基线。两者对比本身就是简历素材
- 存储层必须记录用的是哪个 embedder（维度可能不同）—— 换模型要重建索引

### ⚠️ 实测结果：短板被精确量化了（2026-10 补充）

当初写的是定性判断"语义泛化弱"。用 30 条评估集跑完，它变成了具体数字：

| k | dense recall | dense MRR |
|---|---|---|
| 1 | 0.3462 | 0.3462 |
| 5 | 0.6538 | 0.4545 |
| 20 | 0.8462 | 0.4694 |
| 50 | 0.9615 | 0.4721 |
| 100 | **1.0000** | 0.4726 |

**读法**：recall@100 = 100% 说明**它从不"找不到"**（26 个目标全部在候选里），
但 MRR 从 0.4545 到 0.4726 几乎不涨 —— 说明**它排不好**，
把大量不相关块放在了前面。

原因具体到机制：评估集里很多问题是**改写问句**
（问"为什么日志要用 flush handler"，文档里写的是"块缓冲"），
字符 n-gram 只认字面重叠，这种问句自然排不到前面。

### 由此得到的最重要一条结论

> **想在 RAG 上拿到好看的数字，换 embedding 比调检索算法有效得多。**

这条结论只有先跑出基线才说得出来。它直接决定了后续的投入顺序：
先解决 embedding（需要 API Key 或本地模型），再谈 rerank、混合权重这些细节。

**这也是"下限基线"设计的价值**：如果一开始就用真实模型，
你只会看到一个还不错的数字，**永远不知道算法本身贡献了多少**。

## ADR-003 · 检索层可替换：存储与模型都不锁死

**状态**：已采纳
**日期**：2026-10

### 背景

学习计划第 5 周要求 **pgvector**（含 `ivfflat` / `hnsw` 索引）。
但本机**当前跑不了 Docker**：

| 阻碍 | 状态 |
|---|---|
| CPU 虚拟化（AMD Ryzen 3700X 的 SVM Mode） | ❌ BIOS 里未开启 |
| Windows 版本 | 10 **1903**（Build 18362）；Docker Desktop 要求 22H2（19045+） |
| WSL2 / Hyper-V | 全部 Disabled |
| `registry-1.docker.io` | ❌ 不可达（需配镜像加速器） |

### 决策

**把存储层做成接口，先实现一个不依赖 Docker 的后端，Docker 就绪后新增 pgvector 后端。**

分阶段：

| 阶段 | 向量存储 | 检索方式 | 能学到什么 |
|---|---|---|---|
| **P1（当前）** | SQLite（向量存 BLOB） | numpy 暴力算余弦 | 检索原理、指标口径、切块影响 |
| **P2** | SQLite + `sqlite-vec` 扩展 | 原生向量索引 | **有索引 vs 无索引**的速度/精度差异 |
| **P3（Docker 就绪）** | PostgreSQL + pgvector | `ivfflat` / `hnsw` | 生产级方案、索引参数调优 |

### 为什么这不是"妥协"

面试时 **"我用过两种实现，知道各自的边界"** 比 **"我只用过 pgvector"** 更有说服力：

- P1 的暴力检索在几百条文档下完全够用 —— 你会**亲身体会到"够用"的边界在哪**
- P2/P3 引入索引后，能给出**具体的加速倍数与 recall 损失**（`ivfflat` 是近似索引，会掉召回）
- 换存储层时检索接口不变 —— 这本身就是"依赖倒置"的实践

### 风险与缓解

- ⚠️ **风险**：如果一直不开 BIOS，就学不到 pgvector。
  **缓解**：BIOS 开启 + 系统升级是独立的小任务，不阻塞 P1/P2。
  而且计划要求 Docker，早晚要做 —— 越早越好。

## ADR-004 · 检索策略：稠密 + 稀疏 + RRF 混合，三者可对比

**状态**：已采纳
**日期**：2026-10

### 背景

纯向量检索有明确的失效场景（计划第 5 周也点名了）：
否定词、专有名词、长查询、跨语言。而纯关键词检索又无法处理同义改写。

实测还发现一个**中文特有的坑**（`probe_env.py`）：

```
SQLite FTS5 默认分词器（unicode61）:
  查询 '函数'    -> 命中 0
  查询 '作用域'  -> 命中 0
  查询 'def'     -> 命中 1

trigram 分词器:
  查询 '作用域'  -> 命中 1
  查询 '函数'    -> 命中 0     ← 2 字查询仍然失败！
```

**trigram 分词器要求查询至少 3 个字符**，而中文里 2 字关键词
（向量、切片、函数、召回、降级）极其常见 —— **这个限制不能接受**。

### 决策

**三通道，且都要能单独跑、用同一套评估集对比：**

| 通道 | 实现 | 定位 |
|---|---|---|
| **稠密** | 本地 n-gram 向量 + 余弦 | 主力。中文友好、能抓改写 |
| **稀疏** | **自建字符 n-gram 倒排索引**（不用 FTS5） | 补精确匹配；2 字词也能命中 |
| **混合** | **RRF（Reciprocal Rank Fusion）** 融合两路排名 | 通常最优；RRF 简单、不需要调权重 |

**为什么自建倒排而不用 FTS5**：FTS5 的 unicode61 对中文按整块切（几乎不可用），
trigram 又不支持 2 字查询。而我们在做 embedding 时**本来就要提取字符 n-gram** ——
顺手建倒排，成本几乎为零，且完全可控。

### RRF 为什么优于加权求和

```
RRF(d) = Σ  1 / (k + rank_i(d))        k 通常取 60
```

- **不需要归一化**：稠密是余弦相似度（0~1），稀疏是 BM25 分数（无上界），
  量纲不同，加权求和必须调权重 + 归一化，很脆弱
- **只看排名**：对分数尺度不敏感，鲁棒
- **一个参数**（k），且有成熟默认值

### 影响

- 评估必须**分别报告三个通道的 recall@5 / MRR** —— 这组对比表就是项目的核心产出
- 混合检索不总是最好：如果稠密已经很差，融合也救不回来，要如实报告

### ⚠️ 实测结果：混合**确实**更差，而且能算出来为什么（2026-10 补充）

| 通道 | recall@5 | MRR | hit@1 |
|---|---|---|---|
| dense | 0.6538 | 0.4545 | 0.3462 |
| **sparse** | **1.0000** | **0.7558** | **0.6154** |
| hybrid（RRF） | 0.7692 | 0.5942 | 0.4615 |

直觉是"混合一定比单一好"。**实测 hybrid 低于纯 sparse。**
ADR-004 里我写的是"混合通常最优"，这个预判**被推翻了**。

原因在 RRF 的公式本身：

```
RRF(d) = Σ 1/(k + rank_i(d))        k = 60
```

关键：用的是**排名**不是分数。两路各取 pool=30 个候选，于是：

- sparse 排第 1 的块 → `1/61 ≈ 0.0164`
- **dense 排第 1 的块（可能完全不相关）→ 也是 `1/61 ≈ 0.0164`**

dense 的 30 个候选里即使大多不相关，也每个都拿到 `1/61 ~ 1/90` 的分。
稀疏的排名本来是准的，但候选池被稠密塞进了 30 个"排名靠前却不对"的块，
融合后真正的好结果被挤到后面。

**教训**：

> 混合检索的前提是**两路都别太差**。一路明显弱时，融合只会拉低整体。
> 正确做法是先提升弱通道（换 embedding，见 ADR-002 的实测补充），
> 或者给弱通道降权 —— 但降权必须有数据支撑，不能凭感觉调。

**一个反直觉的推论**：RRF "对分数尺度不敏感"是它的优点，
但在**某一路整体失准**时，这个优点就变成了缺点 ——
因为它无法识别"这一路的第一名其实很垃圾"。
加权求和反而能通过权重压制弱通道（前提是你知道该给多少）。

## ADR-005 · 评估集：50 条以上，必须可复现、可门禁

**状态**：已采纳
**日期**：2026-10

### 背景

学习计划明确写了：**"建 50 条评估集（这一步决定了你后面所有优化是否有意义）"**，
以及"基线纯向量检索 recall@5 有明确数值记录（通常 0.5–0.7），不靠感觉"。

没有评估集，RAG 就只能靠"试几个问题看看"——那不是工程，是玄学。

### 决策

**评估集格式**（`eval/questions.jsonl`，一行一条）：

```json
{"id": "q001", "question": "章节重排后 def 在第几章教？",
 "answer": "第 04 章", "gold_doc": "python_basics/docs/04-函数.md",
 "type": "fact", "difficulty": "easy"}
```

**硬性要求：**

1. **≥ 50 条**，覆盖多种类型：事实查找、跨段推理、代码相关、**不可答（应拒答）**
2. **gold_doc 必须真实存在**并在脚本里校验 —— 否则指标算的是错的东西
3. **指标可复现**：同一个 embedder + 同一个索引 → 指标每次一样
4. **带门禁**：`--fail-under recall@5=0.6`，指标掉了就返回非 0（可用于 CI）

**指标定义（写清口径，避免自欺）：**

| 指标 | 定义 |
|---|---|
| `recall@k` | 前 k 个结果里**包含 gold_doc 的查询比例**。分母是**所有查询**（含不可答的？—— 不含，不可答题单独算） |
| `MRR` | 第一个命中结果的排名倒数的平均。**比 recall@k 更敏感**：命中了但排第 5 vs 排第 1，这里能区分开 |
| `拒答准确率` | 不可答题里，系统正确拒答的比例（避免"什么都敢答"） |

### 关于 50 条怎么来（诚实说明）

题必须是**有真实答案的**，不能编。做法：

- 语料是仓库自己的文档，内容我完全掌握 → 可以基于文档事实出题
- 每条题必标注 `gold_doc`，并在生成脚本里**校验该文件存在**
- 主观题（"这段代码好吗"）不入评估集 —— 无法机械判定

**这一步不能省、也不能糊弄。** 评估集造假 = 后面所有指标都没有意义。

## ADR-007 · 重排：两段式（粗召回 + 词法成对打分），因为瓶颈是"排不好"

**状态**：已采纳
**日期**：2026-10

### 背景：有明确的数据指向

ADR-002 的实测发现：

    dense  recall@5   = 0.6538    MRR = 0.4545
    dense  recall@100 = 1.0000    MRR = 0.4726      ← 关键

recall@100 已经是 100%（26 个目标全都进了候选），但 MRR 几乎不涨。
**结论：瓶颈不是"找不到"，是"排不对"。**

这个诊断直接决定了该做什么：重排的价值就在于"先保证召回、再提升排序"。

### 决策

**两段式检索：**

```
第一阶段（召回）：union of dense@50 + sparse@50（交错合并）
第二阶段（精排）：词法成对打分（LexicalReranker）
```

**为什么第一段用 union 而不是 RRF 融合**：
RRF 在融合时就把弱通道的坏排名"焊"进结果（ADR-004 已实测确认），
而 union 只是扩大候选池，**把排序的判断权留给重排器** ——
重排器能看到 chunk 原文，比 RRF 只看排名信息更多。

**⚠️ union 必须"交错"合并，不能先 dense 后 sparse 拼接。**
第一版是拼接，实测导致一个 gold 被挤出候选池：

    sparse       recall@50 = 1.0000     ← 完美
    union(50+50) recall@50 = 0.9615     ← 反而缺了一个

原因：同一个块可能被两路都召回，dense 的 50 个（含重复）先把名额占了，
sparse 里那些**只有 sparse 能找到**的块被挤到池外。
改成交错（dense[0], sparse[0], dense[1], sparse[1], …）后 recall@50 = 1.0000。

**为什么不用神经网络交叉编码器**：
没有 API Key；本地跑 cross-encoder 需要 torch + 模型（几百 MB），
本机网络不稳。那是最理想的方案，但不该成为"今天什么都做不了"的理由。
所以实现了一个**词法交叉编码器**：它同样是"query 与 chunk 放在一起看"
（而非各自编码算余弦），只是打分函数是词法特征。

**三个候选信号**：IDF 加权词重叠、标题命中、查询词邻近度。

### 实测结果

26 条可答题，切块 heading，k=5：

| 通道 | recall@5 | MRR | hit@1 |
|---|---|---|---|
| dense | 0.6538 | 0.4545 | 0.3462 |
| **sparse** | **1.0000** | **0.7558** | 0.6154 |
| hybrid（RRF） | 0.7692 | 0.5942 | 0.4615 |
| **rerank** | 0.9231 | 0.7532 | **0.6538** |

**诚实的结论：重排没有超过纯 sparse。**

与 sparse 相比：recall@5 低 0.077（2 条题），MRR 低 0.003（几乎持平），
**hit@1 高 0.038（反超）**。

但**对比 hybrid（同样用了两路信息）**，重排的改善是压倒性的：

| | recall@5 | MRR | hit@1 |
|---|---|---|---|
| hybrid（RRF 融合） | 0.7692 | 0.5942 | 0.4615 |
| rerank（union + 重排） | 0.9231 | **0.7532** | **0.6538** |
| 提升 | +0.154 | +0.159 | +0.192 |

**所以准确的说法是**：重排明显优于"用 RRF 融合两路"，
但仍然打不过"只用稀疏、不融合"。根因见下面。

### ⚠️ 权重扫描：两个发现，其中一个推翻了我的设计

系统扫描（`eval/sweep_rerank.py`，每格都是完整评估集）：

| heading 权重 | recall@5 | MRR | hit@1 | 池中丢失 |
|---|---|---|---|---|
| 0.0 | **0.9615** | 0.7096 | 0.5385 | 1 |
| **0.3** | 0.9231 | **0.7532** | **0.6538** | 2 |
| 0.8 | 0.8462 | 0.7147 | 0.6538 | 4 |
| 1.5 | 0.8077 | 0.6949 | 0.6538 | 5 |
| 2.5 | 0.6923 | 0.6474 | 0.6154 | 8 |

**发现 1：`heading` 是"用一点 recall 换排序质量"的杠杆，最优点在 0.3。**

我先猜的是 0.8，扫描后改成 0.3。26 条题的 1 条 = 0.0385，
0.3 与 0.0 之间"只差 1 条题"落在巧合区间内，而 hit@1 的 +0.115 更实在。

**发现 2：`proximity`（邻近度）是纯毒药，任何组合下都是负作用。**

看扫描表：`prox=0.0` 的每一行都优于对应的 `prox=0.2` 行。

原因是我第一版的实现有**度量设计错误**：

```python
coverage = (最大命中位置 - 最小命中位置) / len(doc)
score = 1.0 - coverage          # ❌ 用文档长度当分母
```

后果：
- **长而不相关的块**：查询词恰好落在相邻位置 → 分子小 → 得分高
- **短而精准的 gold 块**：查询词分布在整个块里 → 占比大 → 得分低

也就是说，它**系统性地奖励长的噪音块、惩罚短的正确答案**。
另外"只命中一个 n-gram 就返回满分"也是错的（等于给只沾到一个词的块发奖金）。

**已把默认权重设为 0**，函数保留并在 docstring 里写明这组对照数据 ——
留作记录，也方便想复现"它有多糟"时打开。

### 暴露的一个工程问题：默认值有两处来源

CLI 的 `--w-proximity` 默认值（0.3）**覆盖**了 dataclass 的默认值（0.0），
导致"改了默认值但指标没变"，白跑了几轮才定位到。
已改成 CLI 默认值从 `RerankWeights()` 取，**默认值只留一个来源**。

### 影响与后续

- 重排默认关闭，需显式 `--rerank`，不改变原有单通道行为
- `eval/diagnose_rerank.py` 保留分段诊断（召回段 vs 重排段），
  这是定位"该修召回还是该修排序"的工具
- `eval/sweep_rerank.py` 保留权重扫描，任何调参都要用它而不是手调
- **真正的提升方向仍然是换 embedding**（ADR-002）：
  本评估集的问题大量是**改写问句**，而词法重排对"换了说法"无能为力。
  稀疏能做到 recall@5 = 1.0，是因为题面用词与文档高度重合；
  真实用户的问法不会这么"友好"，那时词法方案的劣势会显现。
  **这个局限必须如实说明，不能因为当前数字好看就掩盖。**

### 备选方案与为什么不选

| 方案 | 为什么不选 |
|---|---|
| **神经网络 cross-encoder** | 需要 Key 或 torch + 模型；本地条件不具备。**这是后续升级路径** |
| **只用 sparse、不做两段式** | 在当前评估集上确实最优（recall 1.0）。保留为可选通道，不删 |
| **加权求和融合两路** | ADR-004 已论证：量纲不同、需要调权重、脆弱 |
| **RRF 融合两路** | 已实测：被弱通道拖累（hybrid 全面落后 rerank） |

## ADR-008 · 评估集必须包含足量"改写问句"，否则指标会自欺

**状态**：已采纳
**日期**：2026-10

### 背景：一次让所有指标"变差"的改造

ADR-005 要求评估集 ≥50 条。但补题时发现一个更严重的问题：
**原来的题面用词与文档高度重合**，导致词法检索显得近乎完美。

审计脚本（`eval/audit_questions.py`）量化了这个偏差 ——
它算每条题的查询 n-gram 有多大比例出现在 gold 文档里：

| 分桶 | 改造前 | 改造后 |
|---|---|---|
| 字面重合（≥0.55） | 14 条（53.8%） | 14 条（26.9%） |
| 部分改写（0.35~0.55） | 9 条（34.6%） | 15 条（28.8%） |
| **改写问句（<0.35）** | **3 条（11.5%）** | **23 条（44.2%）** |

### 决策

**评估集必须包含足量改写问句（目标 ≥40%），并把这条写进审计脚本的判定。**

补了 `q031~q056`，其中 `q031~q048` 是**刻意改写**：问法避开文档原词。
例如：

| 题面 | gold 文档里的原词 |
|---|---|
| 前端界面是怎么分发的，为什么没有引入打包工具？ | "Vue 3 走 CDN" |
| 服务端保存了对话上下文吗？ | "完全无状态" |
| 验收时为什么要启动一个真实的服务器进程？ | "真进程 + 真 HTTP" |
| 用户来源字段存在什么数据质量问题？ | "渠道名大小写不一" |

### 实测结果：指标全面下降，但这才是真实水平

改造前后对比（切块 heading，k=5）：

| 通道 | 旧 30 条（宽松） | 新 56 条（含 44% 改写） | 变化 |
|---|---|---|---|
| dense | 0.6538 | 0.4615 | **−0.192** |
| **sparse** | **1.0000** | **0.9038** | **−0.096** |
| hybrid | 0.7692 | 0.7308 | −0.038 |
| rerank | 0.9231 | 0.8462 | −0.077 |

**最重要的一个数字**：sparse 的 recall@5 从 **1.0000 掉到 0.9038**。

> 旧评估集让稀疏检索看起来完美无缺。**那不是检索好，是题太容易** ——
> 题面用词和文档一样，词法匹配当然满分。
> 这正好印证了 ADR-002 的判断：**词法方案的短板在"同义改写"上**，
> 而旧评估集几乎不含这类题，所以完全掩盖了它。

改造后两路的关系也变了：

| | recall@5 | MRR | hit@1 |
|---|---|---|---|
| sparse | **0.9038** | **0.6478** | 0.5000 |
| rerank | 0.8462 | 0.6385 | **0.5000** |

**hit@1 完全持平**（都是 0.5000），recall 与 MRR 上 sparse 仍略优。
这个结论比改造前更有说服力 —— 因为它是**在有 44% 难题的评估集上**得出的。

### 顺带修正的两个测量错误

**错误 1：用"位置名次"衡量 union 的召回。**

诊断脚本对 union 也算了 `recall@50`，但 union 的池子有 50~100 个候选，
"名次"只是**展示顺序**（两路交错排列），不代表它被截断了。
于是量出 union recall@50 = 0.9808 < sparse 的 1.0000，
看起来像"合并策略又坏了"，其实是**口径错了**。

正确口径：**只看 gold 在不在池子里**（池子大小就是它的 recall@池）。
按这个口径测：union recall@池 = **1.0000** —— 它确实比任何单路都好。

> 教训：**指标口径错了，比没有指标更危险** —— 它会让你去修一个不存在的问题。

**错误 2：写死"1 条题值多少"。**

`eval/sweep_rerank.py` 里印着"26 条题，1 条 = 0.0385"，那是硬编码。
评估集扩到 52 条可答题后，1 条只值 **0.0192** ——
判断"什么算改进"的门槛整个错位，很多噪声会被当成收益。
已改成动态计算。

### 影响

- 所有历史指标对比**必须注明评估集版本**，不能混着比（旧 30 条的数字已不适用）
- 门禁阈值要用新基线重设（sparse recall@5 现在是 0.9038，不再是 1.0）
- **这是接入真实 embedding 前的必要准备**：有了 44% 的改写问句，
  换模型带来的提升才量得出来；在旧评估集上换什么都没法提升（已经是 1.0）

## ADR-009 · LLM 重排：用对话模型补上词法方法缺的语义信号

**状态**：已采纳
**日期**：2026-10

### 背景：词法重排的败因已经被精确定位

ADR-007 实测：**词法重排打不过纯 sparse**（recall@5 0.8462 vs 0.9038）。
ADR-008 进一步指出：加入 44% 改写问句后，sparse 掉的正是"换了说法"的题。

所以这一层的定位很清晰：**提供词法方法拿不到的那个信号 —— 语义。**

### 决策

**用 LLM 做 pointwise 批量打分，作为两段式的第二段。**

### 关键前提：DeepSeek **不提供 embedding 端点**（实测）

拿到 Key 后先探测（`ai-lab/tools/probe_deepseek_api.py`）：

| 端点 | 结果 |
|---|---|
| `GET /models` | ✅ 200，可用模型 `deepseek-flash`、`deepseek-v4-pro` |
| `POST /embeddings` | ❌ **404** |
| `POST /chat/completions` | ✅ 200 |

**所以这个 Key 不能用来做向量化**（那是 RAG 的另一半需求），
但**非常适合做 LLM 重排与生成层**。这次先做重排 —— 因为它正对当前瓶颈。

### ⚠️ 三个坑，第一个最隐蔽

**坑 1：`deepseek-flash` 是推理模型，`max_tokens` 给小了会永远拿到空内容。**

我最初按"只要一个数字"设 `max_tokens=4`。结果是：

```json
{"content": "", "reasoning_content": "我们需要回答用户中文", "finish_reason": "length"}
```

**`content` 永远是空的** —— 因为它是推理模型：先吐 `reasoning_content`（思维链），
`content`（最终答案）在思维链**之后**。预算太小就连思维链都写不完。

实测阈值（同一提示词，只改 max_tokens）：

| 模型 | max_tokens | 推理 token | content |
|---|---|---|---|
| deepseek-flash | 4 / 64 | 4 / 64 | **空** |
| deepseek-flash | 256 | 160 | `'10'` |
| deepseek-v4-pro | 256 | 147 | `'10'` |

**坑 2（更严重）：我把失败静默成了 0 分。**

第一版的异常处理是 `except Exception: score = 0.0`。
于是"36 次调用、35 次失败"这件事**完全看不出来** ——
所有候选都被打成 0 分、排序没有任何变化，
现象上看起来像"**LLM 重排在评估集上没效果**"。

> **把失败伪装成数据，比直接崩掉危险得多。**
> 崩掉你立刻知道要查；伪装成 0 分，你会去调提示词、换模型、怀疑方法本身 ——
> 而真正的问题是"一次都没成功"。

已改成：重试有限次，**最终仍失败就抛出异常**，并把最后一次错误原文带出来。

**坑 3：批量不是越大越好，推理 token 会剧烈波动。**

参数网格扫描（`eval/probe_batch_limits.py`，用真实语料块）：

| 批 | 截断 | max_tokens | 结果 | prompt | 推理 | 耗时 |
|---|---|---|---|---|---|---|
| 10 | 400 | 1500 | ✅ 10 条 | 1682 | 132 | **1.1s** |
| 10 | 800 | 1500 | ✅ 10 条 | 2075 | 593 | 3.3s |
| 15 | 400 | 2500 | ✅ 15 条 | 2700 | 2361 | 12.1s |
| 15 | 800 | 2500 | **❌ 截断** | 3248 | **2500** | 12.0s |

**注意推理 token 那一列：同一格从 80 到 2361 都出现过。**
它不是输入长度的线性函数 —— 所以 `max_tokens` 不能贴着"平均值"给，
必须留足余量（默认 1500）。而 15×800 那格把 2500 预算全烧在推理上，
**仍然拿不到答案**。

### 批量 vs 逐条：不是"省一点"，是"能不能用"

`eval/probe_batch_scoring.py` 的实测（5 个候选，含 1 个明显相关、1 个部分相关）：

| | 逐条 | 批量 |
|---|---|---|
| 调用次数 | 5 | **1** |
| token | 1105 | **796**（省 28%） |
| 解析结果 | `[10, 0, 0, **None**, 0]` | `[10, 0, 0, 2, 3]` |

**逐条那次有一个候选返回了 `None`** —— 因为它的推理没在预算内写完。
批量把推理开销摊到多个候选上，反而更稳。

而且分数分布也更好：逐条是 `[10,0,0,0,0]`（几乎二值化，重排退化成过滤），
批量是 `[10,0,0,2,3]`（有梯度，排序才有信息）。

### 实测结果（全量 52 条可答题）

| 通道 | recall@5 | MRR | hit@1 | 耗时 |
|---|---|---|---|---|
| dense | 0.4615 | 0.2833 | 0.1731 | 0.5s |
| sparse | 0.9038 | 0.6478 | 0.5000 | 0.3s |
| hybrid（RRF） | 0.7308 | 0.4821 | 0.3077 | 0.8s |
| rerank（词法） | 0.8462 | 0.6385 | 0.5000 | 1.1s |
| **llm（语义重排）** | **0.9808** | **0.8638** | **0.7885** | 2873s |

**LLM 重排 vs sparse：**

| 指标 | sparse | llm | 提升 |
|---|---|---|---|
| recall@5 | 0.9038 | **0.9808** | **+0.077** |
| MRR | 0.6478 | **0.8638** | **+0.216（+33%）** |
| hit@1 | 0.5000 | **0.7885** | **+0.288（+58%）** |

**这是本项目最关键的一张表。** 它把前面几条 ADR 的推断全部验证了：

- ADR-002 说"词法方案的弱点是同义改写" → ADR-008 用 44% 改写问句验证了
- ADR-007 说"词法重排打不过 sparse，因为和它用的是同一类信息" → 实测确认
- **本 ADR**：补上语义信号后，**hit@1 从 0.50 提到 0.79** ——
  说明"排不好"这个瓶颈确实是语义能力不足造成的，不是算法问题

代价：**2873 秒 vs 0.3 秒（约 11000 倍）**。

### 📉 成本-效果曲线：15 个候选就饱和了

`eval/sweep_llm_candidates.py`（用已缓存打分重算，**零 API 调用**）：

| 候选上限 | recall池 | recall@5 | MRR | hit@1 | 打分次数 | vs全池 |
|---|---|---|---|---|---|---|
| 5 | 0.7115 | 0.7115 | 0.6619 | 0.6346 | 260 | 6% |
| 10 | 0.9423 | 0.9231 | 0.8221 | 0.7500 | 520 | 12% |
| **15** | 0.9423 | **0.9423** | **0.8606** | **0.8077** | 780 | **17%** |
| 20 | 0.9423 | 0.9423 | 0.8606 | 0.8077 | 1040 | 23% |
| 50 | 0.9808 | 0.9423 | 0.8510 | 0.7885 | 2600 | 58% |
| 95 | 1.0000 | 0.9808 | 0.8638 | 0.7885 | 4475 | 100% |

**两个反直觉的发现：**

1. **15 个候选就饱和了。** 从 15 加到 95 是 **5.7 倍成本**，
   换来 MRR +0.003（≈0.15 条题）—— 纯浪费。

2. **给太多候选反而伤 hit@1**：15 个时 hit@1 = 0.8077，
   95 个时降到 0.7885。**候选太多会引入噪音，把正确答案挤下去。**

> 所以生产环境该用 `--llm-max-candidates 15`。
> 报告里的 0.9808/0.8638 是**全池（95 个）**的数字，默认值保持 50/95
> 是为了让那条命令可复现；日常用 15 即可，成本只有 17%。
>
> **注意**：15 个的 recall池上限是 0.9423（有 3 条题的 gold 不在前 15 名里），
> 所以 recall@5 会从 0.9808 降到 0.9423。这是"省钱"必须付的代价，
> 该按场景选：**答案质量优先选全池，成本优先选 15。**

### 成本

- 缓存是**必须的**：按 (模型, 问题, 单个段落) 存哈希 →
  换批次划分不会失效，重跑同一批题几乎不花钱
- 全量 52 题 × 95 候选 ≈ 4475 次打分（448 次批量调用），
  缓存文件 194 KB
- deepseek-flash 很便宜，量级在**几毛钱人民币**

### 一个进程管理教训：长任务必须有可观察的进度

第一版只在**整轮评估结束后**才存缓存。于是跑全量时：
进程跑了 20 多分钟，磁盘上的缓存文件**一直不更新**，
看起来像卡死，我就把它杀了 —— **前面花钱买到的打分全丢了**。

实际它一直在正常工作（并发 3、每批 0.8~1.4 秒、零限流）。

> 教训：**没有进度可看，人就会误判成故障；误判成故障就会去杀它，
> 然后丢掉真实进度。** 已改成每 50 次调用落一次盘
> （`LLMScorer.maybe_save_cache`）。
>
> 另外还专门测过限流（`eval/probe_rate_limit.py`）：并发 3 时
> 每批 0.8~1.4 秒、零 429。**"慢"就是真的工作量大，不是被限流。**

### 与 ADR-007 的关系（为什么两个都保留）

| | 词法重排 | LLM 重排 |
|---|---|---|
| 信号 | 字面重叠 + 标题 | **语义**（能处理改写问句） |
| recall@5 | 0.8462 | **0.9808** |
| MRR | 0.6385 | **0.8638** |
| hit@1 | 0.5000 | **0.7885** |
| 成本 | 免费 | 每次评估几毛钱 |
| 速度 | 毫秒 | 分钟级 |
| 依赖 | 无 | API Key |

两个都留在代码里，**用同一套评估集对比**。
词法重排不是白做的：它是"零成本基线"，能回答
"**这笔 API 钱到底买到了多少效果**" —— 这正是该讲的取舍。

### 备选方案与为什么不选

| 方案 | 为什么不选 |
|---|---|
| **listwise 排序**（一次给所有候选排序） | 一次改一个候选就要重算全部；且难缓存。pointwise 的分数可跨查询复用 |
| **逐条打分** | 实测更贵（token +28%）**且更不稳**（会返回 None） |
| **本地 cross-encoder** | 需 torch + 模型；本机网络不稳。仍是后续可选项 |
| **DeepSeek embedding** | **不存在这个端点**（实测 404）。向量化需另找来源 |
