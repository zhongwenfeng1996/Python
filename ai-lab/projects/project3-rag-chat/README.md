## 怎么跑

```powershell
$py = "G:\转型\.venv\Scripts\python.exe"
cd G:\转型\ai-lab\projects\project3-rag-chat

# 需要 API Key（重排与生成都用它）—— 放在项目二的 .env 里
#   ai-lab/projects/project2-rag/.env  ->  DEEPSEEK_API_KEY=sk-...

& $py backend\main.py                 # 默认 http://127.0.0.1:8000
& $py backend\main.py --port 8010     # 换端口
& $py backend\main.py --no-warm       # 跳过缓存预热（起得快，但首个问题要等几十秒）
```

启动时会**预热示例问题的打分缓存**（约 1 分钟）。这一步很关键：

| | 首字延迟 | 说明 |
|---|---|---|
| 冷缓存 | **53 秒** | 重排要给 86 个候选打 LLM 分（9 次调用），`sources` 必须等整批打完 |
| **预热后** | **1.7 ~ 2.2 秒** | 分数全部命中缓存 |

> 这不是"作弊"，是把两段式的**成本结构摆到明面上**：
> 重排是"每查询 N 次调用"，但**分数与问题绑定、与用户无关**，可以离线预烧；
> 生成是"每查询 1 次调用"，必须实时。
> 生产里同样可以预热高频问题，冷门问题接受慢一点。
>
> 实测预热后：**1.71s / 2.15s / 1.88s / 0.21s**（最后一条是离题题，
> 分数低于阈值直接弃答，**一次 API 调用都没发**）。

打开页面后建议**按这个顺序点**（每条示例都标了"能答/该弃答"）：

| 点这条 | 看什么 |
|---|---|
| 项目一现在有多少条测试通过？ | 出处先出现，正文逐字冒出来，引用可点 |
| 前端界面是怎么分发的，为什么没有引入打包工具？ | 改写问句也能答（词法方案会失败的那类） |
| **项目一的测试用例文件叫什么名字？** | **该弃答** —— 项目二有类似信息，但机械校验会拦下 |
| **这个仓库的 GitHub star 数是多少？** | **该弃答** —— 语料里不可能有 |
| **Transformer 的注意力机制时间复杂度是多少？** | **该弃答** —— 完全离题 |

> 最后三条是**演示重点**：一个不会说"不知道"的 RAG 在生产里是负资产。

## ⚠️ 踩过的一个坑：SQLite 的线程限制会让服务"看起来卡死"

第一次跑端到端时 `/api/ask` **180 秒超时**。分段计时显示整条链路很快
（召回 0.01s / 重排 0.27s / 生成 3.9s），所以问题不在链路。

真因是：

```
sqlite3.ProgrammingError: SQLite objects created in a thread can only be
used in that same thread.
```

- `Store` 的连接在**主线程**（启动时）创建
- 检索段在**线程池**里跑（为了不阻塞事件循环）
- → 第一次请求就抛异常

**而症状极具误导性**：`/api/ask` 是异步生成器，第一段检索就抛异常
→ `StreamingResponse` **连响应头都没发出去** → 客户端一直等到超时，
**看起来像"服务卡死"，真实原因是一句话的线程限制。**

修法：`check_same_thread=False` + 一把 `RLock` 把访问串行化
（`check_same_thread=False` 本身不保证并发安全，它只是解除限制）。
改完复测：

```
主线程直接调       0.28s  ✅
线程池里调         0.19s  ✅   ← 之前这里报 SQLite 错
事件循环 executor  0.18s  ✅
```

> 这个坑之所以在评估脚本里从没出现：**评估全程单线程**。
> 只有把它接到 Web 服务上才会暴露 —— 这也说明"能跑通"和"能服务"是两件事。

## 设计取舍

| 决定 | 为什么 |
|---|---|
| **复用 project2-rag 的模块**（sys.path 指过去），不拷一份 | 拷一份就会分叉：改了评估里的检索、网页还是旧的，两边数字对不上。这个项目上我已经因为"同一逻辑两份实现"吃过一次亏（ADR-008 的 union 忘了同步） |
| **先推 sources 再流式推正文** | `prepare()` 是同步毫秒级的，所以能先把出处亮出来再生成。用户看到的是"出处立刻出现 + 正文逐字冒出来"，而不是"转圈 3 秒蹦出一整段" |
| **检索段放线程池** | 它是同步的（内部用 `asyncio.run` 跑打分），在 async 端点里直接调会阻塞事件循环，把并发能力废掉 |
| **重排并发 8（评估用 3）** | 网页要的是"别让用户等"，评估要的是"可复现"。实测这批调用没有限流问题（`probe_rate_limit.py`：并发 3 时每批 0.8~1.4 秒、零 429） |
| **打分缓存与评估共用一份** | 评估跑过的问题在网页上**秒回**（0.27s 而不是几秒） |
| **前端 Vue 3 走 CDN，无构建链** | 与项目一同样的取舍（它的 ADR-001）：这个演示的重点是后端链路，不是前端工程化 |
| **机械校验触发后替换正文** | 流式已经把内容推给前端了，所以 `done` 事件里带 `final_text`，前端**必须用它覆盖** —— 否则用户看到的还是被拦下的编造内容 |
| **启动时预热打分缓存** | 冷缓存首字延迟 **53 秒**（重排要给 86 个候选打分），预热后 **1.7 秒**。重排分数与用户无关，可以离线预烧 |

## ⚠️ 第二个坑：冷缓存的首字延迟是 53 秒

功能全对、引用全对，但第一次实测真实问答是：

```
首字延迟: 53.28s   总耗时: 53.39s
```

根因：重排要给约 **86 个候选**打 LLM 分（9 次批量调用），
而 `sources` 事件必须等**整批打完**才能推出去 ——
目标块不在缓存里时，这 9 次调用全要走网络。

> 这正是文档里"命中缓存时秒回"的**反面**：
> **第一次问的题必然是冷的**，而我把命中缓存当成了常态。

修法就是上面的 `warm_cache()`。修完：

```
项目一有多少条测试？        首字 1.71s
前端界面怎么分发？          首字 2.15s
项目一测试文件名？          首字 1.88s  （弃答）
Transformer 复杂度？        首字 0.21s  （弃答，一次调用都没发）
```

最后一行是 ADR-006 那个"分数阈值当省调用的快路径"在起作用：
最高分低于阈值直接弃答，**连生成模型都没调**。

## 接口

```
GET  /              前端页面
GET  /api/health    服务状态（语料规模、模型、阈值、缓存条数）
POST /api/ask       SSE 流式问答   {"question": "..."}
```

SSE 事件序列：

| 事件 | 内容 | 什么时候 |
|---|---|---|
| `meta` | 问题、最高分、送了几段 | 立即 |
| `sources` | 出处列表（编号/路径/标题/分数/预览） | 检索完（毫秒级） |
| `delta` | `{"text": "增"}` | 生成中，多次 |
| `done` | `final_text`、是否弃答、引用、作用域校验结果、耗时 | 结束 |
| `error` | 错误信息 | 异常时 |
